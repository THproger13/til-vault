# 블로그 초안

먼저 `style-guide.md`와 `20-posts/published/`의 최근 발행본 2편(없으면 style-guide의 예시)을 읽는다.

입력: `status: blog`이고 `sensitivity: public`인 노트(묶음이면 여러 개).

**묶음 노트(hub)로 쓰는 긴 글**: 묶음 노트의 "## 개요"를 글 도입과 요약의 뼈대로, "## 하위 개념 지도"를 전체 그림 도표로 쓴다. 하위 답 노트는 `prerequisite` 순서(선행 개념을 먼저)로 한 섹션씩 놓고, 각 섹션은 그 답 노트의 사실·예제·도표·출처를 재료로 아래 "글로 다시 쓰기" 규칙대로 쓴다. 하위 노트끼리 겹치는 설명은 한 번만 쓰고 뒤 섹션에서 앞 섹션을 가리킨다. 씨앗은 "다음에 볼 개념"에 이 글과 가장 가까운 3개까지만 이름과 한 줄 설명으로 쓴다. `source_notes`에는 묶음 노트와 들어간 답 노트를 모두 적는다. 사용자가 대화에서 노트를 직접 지정하면 `draft`·`reviewed`여도 쓰되, 먼저 그 노트를 `blog`로 바꿀지 물어본다. `post_format`이 `none`이면 `short`로 쓴다.

`templates/post.md` 순서를 지킨다.
1. 검색 의도가 드러나는 제목 (문제·키워드 중심)
2. 요약 3줄 (결론부터)
3. 문제 상황 (재현 가능한 맥락, 버전, 증상. 회사 정보 일반화)
4. 원리와 Mermaid 도표 (필수)
5. 해결과 선택지 비교, 트레이드오프
6. 직접 해본 결과: 원본 메모를 뼈대로 쓴다. 원본 메모에 없는 수치·경험을 지어내지 않는다. 비어 있으면 "[직접 작성]"으로 둔다
7. 함정과 주의점
8. 참고 자료 (공식 문서 우선, 실제로 확인한 링크만)
9. 작성일·버전·수정 이력

## 글로 다시 쓰기 (가장 중요)
노트는 재료이고 초안은 글이다. **사실·수치·코드 예제·도표·출처 링크는 노트에 있는 것만 쓰되, 문장은 `style-guide.md`의 말투로 처음부터 다시 쓴다.** 노트 문장을 복사해 붙이지 않는다.

- **새 사실은 만들지 않는다**: 노트에 없는 주장·수치·예제·경험을 추가하지 않는다. "## 코드 예제"는 코드 그대로 가져온다. 노트에 풀이가 빠져 있으면 초안 맨 위에 "노트 보강 필요: …"를 적는다. 업무 코드는 어떤 경우에도 넣지 않는다.
- **문단으로 쓴다**: 설명은 목록이 아니라 문단으로 쓴다. 목록은 명령어 옵션, 확인 체크리스트, 요약 3줄처럼 나열이 본질인 곳에만 쓴다.
- **잇는다**: 각 문단 첫 문장은 앞 문단을 받아서 시작한다. 새 개념·표·코드·도표를 꺼내기 전에 왜 지금 필요한지 한 문장으로 말한다.
- **인용**: 영어 원문 인용 블록(`> "..."`)은 글 전체에 2개까지, 원문 표현 자체가 중요한 곳에만 쓴다. 나머지는 한국어로 풀어 쓰고 문장 끝에 `([문서 이름](URL))` 링크만 건다. 출처 링크는 빼지 않는다.
- **약어·명령어 풀이**: `> 약어:` 블록을 만들지 않고, 처음 나오는 문장 안에서 괄호로 푼다. 이 글을 이해하는 데 필요한 것만 푼다. "이름 유래: 문서 근거 없음", "약어 아님" 같은 노트용 표기는 쓰지 않는다.
- **한 번만 말한다**: 같은 주장은 글에서 한 번만 쓴다(요약 3줄은 예외). 표와 도표가 같은 내용이면 하나만 남긴다. "함정과 주의점"에는 본문에서 이미 설명한 것을 다시 풀지 않고 한 줄로만 짚는다.
- **작업 내부 용어 금지**: 씨앗, 허브, 원본 노트, `check` 상태, 답 노트, inbox, "위 N번 인용" 같은 볼트·파이프라인 용어는 본문에 쓰지 않는다. 작성자에게 남길 말은 초안 맨 위 메모(`> 발행 전 확인: …`)에만 쓴다.
- **쉽게 읽히게**: `CLAUDE.md` "쉽게 읽히게"를 따른다. 도입 끝에서 글 전체에 쓸 예시와 이름을 한 번 소개하고, 본문·코드·도표에서 같은 이름을 쓴다. 구성 요소는 처음 나올 때 역할을 한 문장으로 말한다. 설명한 개념이 코드·설정 어디에 나타나는지 보여 주는 예제가 반드시 있어야 하고, 코드 뒤에는 "이 코드에서 ~는 이 줄이다"와 예시 데이터의 흐름을 문장으로 쓴다. 노트에 그런 예제가 없으면 지어내지 않고 초안 맨 위에 "노트 보강 필요: 개념을 선언하는 예제 없음"을 적는다.
- **왜 필요한가**: "원리"의 첫 부분에서, 정의보다 먼저 이 개념이 왜 필요한지를 한 문단으로 쓴다. 이게 없으면 어떤 문제가 생기는지, 그 기술의 어떤 특성 때문에 생긴 문제인지를 짚는다. 재료는 노트의 `### 왜 필요한가`와 노트에 이미 있는 출처 달린 사실이다. 노트에 재료가 없으면 지어내지 않고 초안 맨 위에 "노트 보강 필요: 왜 필요한지 설명 없음"을 적는다.
- **예제 기준 버전**: 코드·설정·명령어 예제 바로 위에 `> 예제 기준: 소프트웨어 이름 버전`을 쓴다(정확한 제품명, 관련 미들웨어·프레임워크 모두). 노트의 표기를 그대로 쓰고, 노트에 없으면 근거 문서 링크에서 확인되는 버전만 쓴 뒤 초안 맨 위에 "발행 전 확인: 예제 버전"을 적는다. 추측하지 않는다. 같은 내용을 속성 `version_info`에도 적는다.
- **도입**: "문제 상황"은 사용자가 실제로 남긴 기록(원본 메모, `situation`, inbox의 상황 한 줄, "## 복습 기록"의 "내 대답"에 남은 오개념)을 재료로 "처음엔 이렇게 알고 있었다 → 알고 보니"로 쓴다. 기록에 없는 계기나 감정은 지어내지 않는다. 재료가 없으면 독자가 가질 법한 의문으로 시작한다.
- **소제목**: 템플릿의 섹션 이름(요약, 문제 상황, 원리, 직접 해본 결과, 참고 자료)은 남기되, 뒤에 `: 내용을 드러내는 질문이나 문장`을 붙여도 된다. "해결과 선택지 비교"는 글 내용에 맞는 제목으로 바꿔도 된다.
- **마무리**: "지금까지 ~를 알아보았다"로 핵심을 한 번 정리하고 다음에 볼 내용으로 넘긴다. 사용자가 남기지 않은 감상("정리하면서 느낀 것은…")을 지어내지 않는다. 마지막에 강조할 한 가지는 본문에서 출처로 뒷받침한 사실을 그대로 쓰고, "A보다 B가 더 ~하다" 식의 비교는 본문에서 실제로 비교한 것이 아니면 쓰지 않는다.

저장 전 자가 점검: ① 영어 인용 블록 2개 이하 ② 목록 줄이 전체의 1/3 이하 ③ 같은 어미로 끝나는 문장이 4번 연속 없음 ④ 내부 용어 없음 ⑤ 노트에 없는 사실 없음 ⑥ "왜 필요한가" 문단 있음 ⑦ 모든 예제 위에 `예제 기준` 줄 있음 ⑧ 설명한 개념마다 그것을 선언·지정하는 코드 줄이 있음 ⑨ 본문·코드·도표의 예시 이름이 같음. 어긴 곳은 그 부분만 다시 쓴다.

짧은 글 최소 기준: 도표 1개, 경험 문단 1개, 공식 출처 1개. 못 채우면 초안 맨 위에 "발행 보류: 사유"를 적는다.

`20-posts/drafts/YYYY-MM-DD-slug.md`로 저장한다. 초안 맨 위 속성에 `source_notes: ["[[노트명]]"]`을 남긴다. 원본 노트는 `status: drafted`, `drafted_at`, `draft_path`만 바꾸고 본문은 고치지 않는다. 사용자가 할 일 3가지(경험 문단 다듬기, 도표 확인, publish-guard)를 알려준다.
